  1. 01
    Stage 01

    The computer only sees bytes

    Before anything is a "word" to a model, it's a stream of bytes. Here's your sentence in raw UTF-8, one cell per byte.

  2. 02
    Stage 02

    Bytes get grouped into tokens

    Real models use Byte-Pair Encoding (BPE) or similar, trained on billions of words. This page uses a small illustrative stand-in — greedy prefix/suffix splitting — so you can see the idea: common word-pieces become single tokens, rare ones get split further. The dot (·) marks "start of a new word."

  3. 03
    Stage 03

    Every token becomes a vector

    Click a token above. Each one maps to an embedding — here, a small 12-number vector, generated deterministically from the token itself so the demo is reproducible. In a trained model these numbers are learned so that tokens used in similar contexts end up with similar vectors.

  4. 04
    Stage 04

    Telling the model where each token sits

    Attention on its own is order-blind: comparing Queries and Keys gives the same pairwise scores no matter what order the tokens arrived in, so "dog bites man" and "man bites dog" would look identical to it. The fix is a positional encoding — a vector generated purely from a token's position (using interleaved sine and cosine waves at different frequencies) and added directly onto its embedding.

    Each row below is one position's encoding — 12 values, colored by sign and size. Notice the leftmost columns oscillate fast (fine-grained position) and the right columns oscillate slowly (coarse position) — that mix is what lets the model recover exact and relative position from a fixed-size vector.

  5. 05
    Stage 05

    Tokens look at each other

    Self-attention lets each token pull information from every other token, weighted by relevance. Click a row to see what that token attends to (weights computed live via softmax over toy Query·Key scores — first 10 tokens only, for readability).

    Real transformers don't run this once — they run it several times in parallel, called multi-head attention, then concatenate the results and mix them with one more linear layer. Switch heads to see how the same tokens produce different attention patterns depending on which projection is looking at them.

    Click any row label to focus a token.

  6. 06
    Stage 06

    Keeping the signal, then thinking about it

    Two more ideas make this trainable at depth. A residual connection adds each sub-layer's input back onto its output — a guaranteed bypass, so nothing gets lost even in a 100-layer-deep model. Layer normalization then rescales the result before it moves on. Finally, a position-wise feed-forward network expands each token's vector, applies a non-linearity, and contracts it back — the same weights applied to every position.

  7. 07
    Stage 07

    Stacking the block, many times over

    A real model doesn't run one block — it runs the same shape of block, with independently learned weights, one after another. GPT-2 small stacks 12, GPT-3 stacks 96. Each layer refines the representation a little further: early layers tend to pick up on syntax and local structure, later ones on longer-range meaning.

    Only the feed-forward + residual + normalize half is chained here (attention is stage 05's job) — watch —'s vector keep shifting the deeper it goes:

  8. 08
    Stage 08

    Picking the next token

    The model outputs one probability per vocabulary token. Temperature, top-k and top-p reshape that distribution before a token is drawn. This toy vocabulary is a small hand-built table so the demo stays legible — the math (softmax, filtering, sampling) is real.

This model only knows what got baked into its weights during training. Ask it about a document it has never seen — your team's internal spec, this morning's report — and it will guess fluently and confidently. That guess is a hallucination.

Retrieval-Augmented Generation (RAG) doesn't retrain the model. It finds the relevant text at question-time and hands it to the model as extra context, right before generation. Same Stage 08 sampler — different, better-informed input.

Part B

Grounding the model in a real document

Below is a short internal spec for a fictional project, invented for this page — no model has ever been trained on it. Edit it, ask it a question, and watch retrieval find the right passage before generation runs.

  1. 09
    Stage 09

    Splitting the document into chunks

    Documents are too long to embed as one block, so they're cut into chunks — typically with some overlap, so a fact sitting on a boundary doesn't get orphaned.

  2. 10
    Stage 10

    Embedding chunks into a vector index

    Each chunk is embedded (here: the average of its tokens' toy vectors — a real system uses a trained embedding model) and stored in a vector index. Plotted here in 2D for intuition; real indexes use hundreds of dimensions and approximate nearest-neighbor search to stay fast at scale.

  3. 11
    Stage 11

    Retrieving the closest chunks

    Ask a question. It's embedded the same way, then ranked against every chunk by cosine similarity. Because this demo's vectors are built from shared words rather than learned meaning, retrieval works best when your question reuses a word from the passage — a real embedding model would also catch a paraphrase.

  4. 12
    Stage 12

    Assembling the augmented prompt

    The retrieved chunks are stitched into the model's context window alongside the question and a system instruction. The model itself is unchanged — only its input got richer.

Everything so far produces text and stops. Retrieval made the answer better-informed, but the system still can't do anything — it can't look a live number up, book the thing, file the ticket, or check its own work. And nothing in Parts A or B tells you whether the answer it just gave was actually right.

        
Part C is the rest of the stack: giving a model real actions to take, looping it until the job is done, splitting the job across several narrow agents, and then — because none of that made the model any more honest — proving each claim against a source and measuring whether the whole contraption beats a single well-written prompt.

      


      

        

          Part C
          
From answering to acting — and earning trust

          
Nine more stages, same rule as the rest of the page: every score, ranking, counter and verdict below is computed live in your browser from what you type and click. Nothing is pre-recorded.

        


        
    

          
  1. 
            
    14
    
            
    
              
    
                Stage 14
                
    One search isn't enough
    
              
    
              
    Stage 11 ranked chunks by vector similarity alone. That misses things: embeddings blur exact strings — a version number, an error code, a rare proper noun — into "roughly similar", while a literal keyword search nails those and is helpless against a paraphrase. Hybrid retrieval runs both and fuses the rankings.
    
              
    The fusion here is Reciprocal Rank Fusion — each passage scores 1/(k + rank) in each list, summed. It needs no score calibration at all, which is why it survives two systems that measure completely different things. Watch the middle column: a passage ranked 3rd by both methods often beats one ranked 1st by only one.

    15
    
            
    
              
    
                Stage 15
                
    Handing the model a menu of real actions
    
              
    
              
    A tool is just a function the model is allowed to ask for. Alongside your message, the runtime sends a tool schema for each one: name, description, parameters. The model never runs anything itself — it emits a request naming a tool and its arguments, and the host executes the real function.
    
              
    Here's the part people underestimate: the description is not documentation, it's the selection logic. It is the only thing distinguishing one tool from another at choice time. Type a request and watch the match scores; then hit "Vague descriptions" and watch the ranking fall apart without a single word of your request changing.

  3. 
            
    16
    
            
    
              
    
                Stage 16
                
    The loop that turns one answer into work
    
              
    
              
    A single completion can't do multi-step work. The tool-calling loop is what does: send the conversation, run whatever tool the model asked for, append the result as a new message, send the whole thing again. The loop — not the model — is the agent.
    
              
    Two controls matter more than they look. Tool choice decides whether calling is even allowed, and the turn budget is the ceiling that turns a silent infinite loop into a reportable failure. Drop the budget to 2 and watch the run get cut off mid-task.

  4. 
            
    17
    
            
    
              
    
                Stage 17
                
    Making the shape of the answer non-negotiable
    
              
    
              
    "Parse the model's English" is endlessly brittle. Structured output replaces it with ordinary deserialization that either succeeds or fails loudly.
    
              
    The deeper trick is schema as guardrail: mark the evidence fields required, and a claim with no citation can't be represented at all. That's a far stronger promise than an instruction saying "always cite your source", because it's enforced by the type, not by the model's goodwill. When parsing does fail, one bounded repair retry hands the model its own broken output plus the error.

  5. 
            
    18
    
            
    
              
    
                Stage 18
                
    Four shapes for splitting a job across agents
    
              
    
              
    One agent holding twelve tools and a thousand-word brief picks the wrong tool more often than four agents holding three tools each. That's the whole case for multi-agent systems: not extra intelligence, just smaller decisions. Orchestration is the layer that decides who runs when, and it's almost always ordinary code rather than another model.
    
              
    Pick a shape and run it. Every counter is computed from each agent's simulated call cost, and the comparison table underneath scores all four at once — so the trade is visible rather than asserted. Watch what drives the token column: it isn't the number of agents, it's whether each one re-reads a transcript that keeps growing. Group chat is the most expensive thing here by a wide margin, and it never runs an extra agent — it just pays a manager call on every single turn.

  6. 
            
    19
    
            
    
              
    
                Stage 19
                
    Knowing exactly when an agent is finished
    
              
    
              
    Detecting "I'm done, over to you" in free prose is guesswork. A handoff function removes the guessing: a tool that does nothing except exist, so calling it is the signal. An invocation filter watches every call, and the moment a handoff fires it sets a terminate flag — early termination.
    
              
    Turn the filter off and the agent keeps reasoning after it already announced the handoff — extra turns, extra tokens, and a real risk it talks itself into a different decision. Then fire a stall: an agent replying with plain text where a tool call was required, recovered by a bounded nudge rather than a dead workflow.

  7. 
            
    20
    
            
    
              
    
                Stage 20
                
    The step the model is never allowed to take alone
    
              
    
              
    Some actions can't be undone. The durable pattern is that the model does all the judgement — gathering, comparing, recommending — and then stops dead at an approval gate. Two mechanisms enforce it, and the second is the one that actually holds.
    
              
    First, pause & resume: the workflow serializes its state and returns, so a human decision fits a normal request/response cycle instead of blocking a live call. Second, least privilege: before approval the executing tool is not in the agent's kernel at all. Not discouraged by a prompt — absent. Toggle the checkbox and watch what the agent is holding change.

          Part C · trust
          
None of that made the model honest

          
Retrieval improved the odds. Tools gave it reach. Neither established that any particular sentence it produced is true — or that the whole pipeline beats one good prompt. These last two stages are the difference between a demo and something you'd let near production.

        


        
    

          
  1. 
            
    21
    
            
    
              
    
                Stage 21
                
    Proving every claim, then deleting the rest
    
              
    
              
    Grounding is probabilistic; verification is not. After generation, ordinary code takes each claim, resolves its citation, and checks the quoted span actually appears in the source — whitespace-normalized, no model involved. It also checks the source anchor points at a line that exists.
    
              
    Anything that fails is suppressed — struck out, with the reason recorded rather than quietly dropped. Edit the source below: change a number, delete a line, and watch claims flip to suppressed in real time. Then add the injected line and note what does not happen — the verifier doesn't read instructions, only checks strings, so a prompt injection sitting in the data can't talk its way past it.

                Stage 22
                
    Does any of this actually beat one good prompt?
    
              
    
              
    Every stage in Part C added cost. The only honest way to know if it bought anything is an evaluation harness: a fixed golden set with known answers, scored automatically, compared against a baseline.
    
              
    Drag the sensitivity slider. It changes how much the system reports, and you'll see why one accuracy number is a lie: precision and recall move in opposite directions. There is no setting where both hit 100% — the honest question is which error is cheaper for the job you're doing.
