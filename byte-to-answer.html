    The computer only sees bytes

    Before anything is a "word" to a model, it's a stream of bytes. Here's your sentence in raw UTF-8, one cell per byte.

  2. 02
    Stage 02

    Bytes get grouped into tokens

    Real models use Byte-Pair Encoding (BPE) or similar, trained on billions of words. This page uses a small illustrative stand-in — greedy prefix/suffix splitting — so you can see the idea: common word-pieces become single tokens, rare ones get split further. The dot (·) marks "start of a new word."

  3. 03
    Stage 03

    Every token becomes a vector

    Click a token above. Each one maps to an embedding — here, a small 12-number vector, generated deterministically from the token itself so the demo is reproducible. In a trained model these numbers are learned so that tokens used in similar contexts end up with similar vectors.

  4. 04
    Stage 04

    Telling the model where each token sits

    Attention on its own is order-blind: comparing Queries and Keys gives the same pairwise scores no matter what order the tokens arrived in, so "dog bites man" and "man bites dog" would look identical to it. The fix is a positional encoding — a vector generated purely from a token's position (using interleaved sine and cosine waves at different frequencies) and added directly onto its embedding.

    Each row below is one position's encoding — 12 values, colored by sign and size. Notice the leftmost columns oscillate fast (fine-grained position) and the right columns oscillate slowly (coarse position) — that mix is what lets the model recover exact and relative position from a fixed-size vector.

  5. 05
    Stage 05

    Tokens look at each other

    Self-attention lets each token pull information from every other token, weighted by relevance. Click a row to see what that token attends to (weights computed live via softmax over toy Query·Key scores — first 10 tokens only, for readability).

    Real transformers don't run this once — they run it several times in parallel, called multi-head attention, then concatenate the results and mix them with one more linear layer. Switch heads to see how the same tokens produce different attention patterns depending on which projection is looking at them.

    Click any row label to focus a token.

  6. 06
    Stage 06

    Keeping the signal, then thinking about it

    Two more ideas make this trainable at depth. A residual connection adds each sub-layer's input back onto its output — a guaranteed bypass, so nothing gets lost even in a 100-layer-deep model. Layer normalization then rescales the result before it moves on. Finally, a position-wise feed-forward network expands each token's vector, applies a non-linearity, and contracts it back — the same weights applied to every position.

  7. 07
    Stage 07

    Stacking the block, many times over

    A real model doesn't run one block — it runs the same shape of block, with independently learned weights, one after another. GPT-2 small stacks 12, GPT-3 stacks 96. Each layer refines the representation a little further: early layers tend to pick up on syntax and local structure, later ones on longer-range meaning.

    Only the feed-forward + residual + normalize half is chained here (attention is stage 05's job) — watch —'s vector keep shifting the deeper it goes:

  8. 08
    Stage 08

    Picking the next token

    The model outputs one probability per vocabulary token. Temperature, top-k and top-p reshape that distribution before a token is drawn. This toy vocabulary is a small hand-built table so the demo stays legible — the math (softmax, filtering, sampling) is real.

This model only knows what got baked into its weights during training. Ask it about a document it has never seen — your team's internal spec, this morning's report — and it will guess fluently and confidently. That guess is a hallucination.

Retrieval-Augmented Generation (RAG) doesn't retrain the model. It finds the relevant text at question-time and hands it to the model as extra context, right before generation. Same Stage 08 sampler — different, better-informed input.

Part B

Grounding the model in a real document

Below is a short internal spec for a fictional project, invented for this page — no model has ever been trained on it. Edit it, ask it a question, and watch retrieval find the right passage before generation runs.

  1. 09
    Stage 09

    Splitting the document into chunks

    Documents are too long to embed as one block, so they're cut into chunks — typically with some overlap, so a fact sitting on a boundary doesn't get orphaned.

  2. 10
    Stage 10

    Embedding chunks into a vector index

    Each chunk is embedded (here: the average of its tokens' toy vectors — a real system uses a trained embedding model) and stored in a vector index. Plotted here in 2D for intuition; real indexes use hundreds of dimensions and approximate nearest-neighbor search to stay fast at scale.

  3. 11
    Stage 11

    Retrieving the closest chunks

    Ask a question. It's embedded the same way, then ranked against every chunk by cosine similarity. Because this demo's vectors are built from shared words rather than learned meaning, retrieval works best when your question reuses a word from the passage — a real embedding model would also catch a paraphrase.

  4. 12
    Stage 12

    Assembling the augmented prompt

    The retrieved chunks are stitched into the model's context window alongside the question and a system instruction. The model itself is unchanged — only its input got richer.
